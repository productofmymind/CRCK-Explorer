# Patches to rage-formats 0.5.1 (Unlicense, VIRUXE/rage-formats)

Vendored so the Meta writer can be fixed for the archetype editor. Found by rebuilding every `.ytyp` of a retail install and comparing the trees.

1. **Writer, fixed-size float arrays** (`meta_write.rs`, `T_BYTE_ARRAY`): an array member with a float element type (`CLightAttrDef.posn`, `dir`, `tangent`, ... inside `CExtensionDefLightEffect`) was written through the integer path, so each float became the bits of its truncated integer (zeros, denormals, NaN). The reader was right. Now floats are written as floats. About 90 of the 2643 `.ytyp` files of a retail install lost light data before this (the interior files `v_int_*`).
2. **Reader, geometry bone palette** (`ydd.rs`): `DrawableGeometry` now carries `bone_ids` (the palette a skinned geometry's vertex blend indices point into; pointer at +0x68, count at +0x72, the same fields `blocks/drawable.rs` already reads). Added so the viewer can name a skinned geometry after the bone its vertices follow.
3. **Reader, blend indices stored as a Colour** (`vertex.rs`, `to_unified_vertices`): the indices were only taken when the component type was `UByte4`; vehicle geometries store them as `Colour`, so every vehicle vertex read as bone 0. Both types are the raw four bytes.
4. **YFT to XML and back** (`blocks/yft.rs`, `blocks/yft_xml.rs`, `Drawable::read_frag` / `FragTail` in `blocks/drawable.rs`, `Block::owner` in `blocks/mod.rs`): `dump_yft_xml` writes a fragment as XML and `build_yft_from_xml(_checked)` builds the `.yft` (resource version 162) from it. The drawables (main, extra, physics children, the others a pointer scan finds) are typed and editable: a `fragDrawable` is the plain drawable's first 0xA8 bytes, 0xA8..0x150 kept as bytes (a matrix, the pointer to its bound, unnamed fields) and the name pointer at 0x130; drawables that share a shader group, skeleton or joints keep sharing them. **The rest of the system section is not decoded**: the `FragType` header, physics LOD group and LOD, archetype, bounds, articulated body, groups, children, transforms, names and cloth are `<Chunk>`s, byte runs between the typed blocks cut at every block something points at, with each 64-bit word that points into the section replaced by a link (`offset>chunk+offset`, `d<n>` drawable, `p` pages info, `sg/sk/jo<n>` a drawable's shader group, skeleton, joints) and resolved again when the file is laid out. Chunks that were stored back to back stay back to back (`After`, the `Run` block). Name, bounding sphere, bone pose and physics children are written as readable views of those bytes; the checked build refuses an XML where an edit to one of them (or to anything else the chunks decide) does not read back, rather than dropping it. A pointer-looking word that cannot be resolved, a pointer into the graphics section or into a typed block's inside is an error. A `<Fragment>` without `<Chunks>` (another tool's export) cannot be built. Checked on 44 retail `.yft` (8 vehicles with their `_hi`, props, a ped, cloth, prologue props): each reads back as identical XML, builds again to identical XML, and `model-info` of the rebuilt file equals the original's (43 of them). That does **not** show the game loads them (not tried in the game), and it cannot show that a chunk holds no offset or size computed from another block's address.

5. **Clip dictionaries, `.ycd` to XML and back** (`ycd.rs`, `ycd_xml.rs`, `ycd_write.rs`; `Cargo.toml` gets the `ycd_real` test): `parse_ycd` reads the binary (the dictionary, the animation and clip hash tables, animations, the sequence data with all nine channel encodings, clips, tags and properties), `to_xml` / `from_xml` convert to and from the `.ycd.xml` layout Sollumz and CodeWalker use, and `serialize_ycd` writes the binary. A LinearFloat channel is read and then reported as a QuantizeFloat (it cannot be written back as one, and CodeWalker's XML does the same). Virtual-table words are written as zero, as the tools that write `.ycd` do. Checked on real retail files (ped idles, a bar scene, a mime, a seated-on-phone clip, a multi-clip dictionary): the XML equals CodeWalker's after numbers and hash names are normalised, the written binary reads back identically in this reader **and in CodeWalker**, and CodeWalker's own XML goes through `from_xml` and `serialize_ycd` and reads back unchanged. A `.ycd` exported from Blender through Sollumz and built by `from_xml` reads the same in CodeWalker. `tests/ycd_real.rs` runs those checks when `YCD_CHECK_DIR` points at a folder of `x.ycd` next to `x.ycd.xml`; the round-trip unit tests need no game files. That does **not** show the game plays a written file (not tried in the game).

To upstream as PRs; drop this vendored copy once released.
